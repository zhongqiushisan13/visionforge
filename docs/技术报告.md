# VisionForge：面向个人创作者的多模型协同视频生成与可编辑生产管线

**摘要**　针对当前文生视频模型"单次调用、结果不可编辑、失败不可续跑"的工程缺陷，本文提出并实现了一套运行于个人计算机的 AI 视频生产管线 VisionForge。系统将"一句话需求"分解为剧本大纲、分镜表、关键帧、镜头、配音与合成六个阶段，以逐镜头状态机与内容指纹缓存支撑断点续跑和单镜重拍；以配音实测时长反向锁定镜头时长，消除音画错位；以转场链时间轴重算方法将 11 种 `xfade` 转场统一到同一套拼接图，并通过硬切退化策略规避零时长转场导致的片段丢失。系统对图像、视频、语音三类能力做统一抽象，支持云端 API、本地兼容网关与 ComfyUI 工作流三种通道，并可在无任何密钥时以占位素材完成全链路出片。本文报告了系统架构、关键方法与实现细节，并给出开发期的端到端产出记录与稳定性问题分析。实验表明，同一工程在源码形态与打包形态下产出一致（56.04 s / 8.5 MB，4 处转场），在 1280×720、8 镜头配置下可在约 85 s 内完成 44.68 s 成片的合成。

**关键词**　AI 视频生成；多模型协同；状态化流水线；可编辑性；本地部署；视频合成

---

**Abstract**　Current text-to-video systems typically expose a single-call interface: the generated result is neither editable nor resumable, and a single failed shot invalidates the whole sequence. This paper presents VisionForge, a locally hosted production pipeline that decomposes a one-sentence brief into six stages—outline, storyboard, keyframe, shot, voiceover, and composition. Per-shot state machines and content-fingerprint caching enable resumable rendering and single-shot regeneration; shot durations are locked to measured voiceover lengths to eliminate audio-visual drift; a timeline recomputation method unifies eleven `xfade` transitions into one filter graph and degrades hard cuts to a 40 ms blend to avoid segment loss. Image, video, and speech capabilities are abstracted behind a uniform provider interface with cloud, local-gateway, and ComfyUI backends. The system produces a complete video without any API key by falling back to placeholder assets. We report architecture, methods, implementation, and development-time end-to-end runs, including a reproducibility check between source and packaged builds (56.04 s / 8.5 MB, four transitions).

**Keywords**　AI video generation; multi-model orchestration; stateful pipeline; editability; local-first deployment; video composition

## 1 引言

### 1.1 研究背景

扩散模型在图像生成领域的成熟[1,2]直接推动了视频生成的发展。以 Stable Video Diffusion[3] 为代表的开源工作将潜空间扩散扩展到时序维度，商用接口（如 MiniMax-H3）则以异步任务形式提供秒级片段生成能力。对个人创作者而言，生成单个 5 秒镜头的门槛已经很低，但交付一条完整片子仍然困难，原因不在生成质量，而在工程环节：

1. **叙事结构缺失**：模型不理解"起承转合"，需要外部完成分镜与时长规划；
2. **镜头间衔接缺失**：拼接、转场、音画对位、字幕排版均需额外处理；
3. **失败不可恢复**：一次调用失败或一条镜头不满意，往往需要整体重跑；
4. **成本与隐私**：云端按量计费，素材上传涉及内容外流风险。

### 1.2 现有方案的不足

现有一类工具是"提示词 → 单段视频"的封装，交互简单但无法承担叙事任务；另一类是云端一体化 SaaS，功能完整但生成结果与工程文件强绑定于平台，导出能力有限；专业非线性编辑器（NLE，如剪映专业版）具备完整的剪辑能力，却不具备从文本到素材的生成能力。三者之间存在明显空档：**从文本需求到可交付成片，且中间结果可被人工干预的本地化管线**。

### 1.3 本文贡献

本文的设计与实现贡献如下：

1. **可重入的生产管线**：将生成过程建模为逐镜头状态机，配合内容指纹缓存，使"改一句字幕不重算全片、重拍一条镜头不影响其余"成为默认行为；
2. **配音驱动的时长锁定**：以 TTS 实测音频长度反向决定镜头时长，从机制上消除音画错位，而非事后拉伸补偿；
3. **转场链的时间轴重算与硬切退化**：给出重叠时长下的偏移量递推公式，并将零时长转场退化为 40 ms 融合，规避 `xfade` 在 `duration=0` 时吞并后续片段的实现缺陷；
4. **通道无关的能力抽象**：图像、视频、语音三类能力统一为 provider 接口，支持云端 API、本地兼容网关、ComfyUI 工作流与占位实现四类后端，任一环节缺失均可降级；
5. **硬件自适应的实证配置**：以"真实试编码"而非"编码器列表"判定硬件编码可用性，避免在无对应硬件的机器上误选 NVENC 导致渲染失败。

## 2 系统总体设计

### 2.1 设计目标与约束

| 目标 | 具体约束 |
|---|---|
| 本地优先 | 全部计算默认在本机完成，仅模型推理可选云端；服务只监听 `127.0.0.1` |
| 可降级 | 任一模型不可用时，流程仍应产出可播放的成片 |
| 可重入 | 进程中断后可从任意镜头继续，不重复计费 |
| 可编辑 | 生成结果以结构化字段暴露，支持字段级修改与局部重算 |
| 可复现 | 相同参数与相同输入应产出一致结果，打包形态与源码形态行为一致 |

### 2.2 体系结构

系统采用三层结构：表现层（WebView2 宿主 + 单页前端）、编排层（导演器与作业调度）、能力层（provider 适配器），并以文件系统作为唯一持久化介质。

```
┌──────────────────────────────────────────────────────────┐
│ 表现层  WebView2 / 浏览器                                  │
│   工作台 · 剧本 · 分镜 · 时间线 · 成片 · 设置              │
└───────────────┬──────────────────────────────────────────┘
                │ HTTP (127.0.0.1) + 轮询作业日志
┌───────────────▼──────────────────────────────────────────┐
│ 编排层  FastAPI 应用                                      │
│   作业管理器（线程池 / 进度 / 增量日志）                    │
│   导演器 Director：plan → voice → keyframes → clips       │
│                    → render → assemble → revise          │
│   剪辑参数表 / AI 指令解析 / 系统自检                       │
└───────────────┬──────────────────────────────────────────┘

┌───────────────▼──────────────────────────────────────────┐
│ 能力层                                                    │
│   LLM（OpenAI 兼容：DeepSeek / Ollama / vLLM）             │
```

### 2.3 数据模型与状态机

工程以 `project.json` 为唯一事实来源，镜头（Shot）为核心记录单元。主要字段分为四组：

| 组别 | 字段（示例） |

镜头状态迁移如下，任一状态均可被人工编辑打断并重新进入生成：

```
pending ──▶ keyframe ──▶ clip ──▶ ready
   │            │          │
   └────────────┴──────────┴──▶ failed ──(重试/重拍)──▶ pending
```

### 2.4 作业调度

长任务（剧本生成、批量渲染、合成）以作业（Job）形式提交，在固定大小线程池中执行；前端以增量游标轮询日志（`?since=N`），避免重复传输。作业不依赖进程内状态，进程重启后可从 `project.json` 与缓存恢复。

## 3 关键方法

### 3.1 三段式剧本—分镜生成

需求到分镜的映射由三次串行调用完成，而非一次性生成，以降低单次输出的结构复杂度：

1. **大纲**：输出 logline、角色（≤3）、幕结构（beat）与风格锚点；
2. **脚本**：将 beat 展开为场景与台词，约束总时长误差 ±10%；
3. **分镜表**：将场景切分为镜头，约束每条 `duration ∈ [4,10]` 的整数秒，并给出中英双语字幕与英文画面提示词。

结构化输出依赖三层容错：优先请求 `response_format={"type":"json_object"}`；解析失败时按括号平衡扫描从自由文本中抽取首个合法 JSON 对象；仍失败则切换备用模型，最终回退到本地示例分镜。该设计使"模型不支持 JSON 模式"不再是阻断性故障。

需要指出，时长约束是**软约束**。开发期观察到一次目标 18 s 的请求实际产出 52 s 分镜（偏差 189%），系统仅发出告警而不阻断。该现象在第 6.2 节作为局限性讨论。

### 3.2 工作流无关的关键帧生成

关键帧由 ComfyUI 的 `/prompt` 队列生成。为使系统适配用户已有的出图工作流，而非要求用户改写工作流，采用**图重写**策略：遍历 API 格式的节点图，定位 checkpoint 加载节点，插入 `LoraLoader` 节点并将其所有下游消费者重定向至新节点；若无 LoRA 需求则跳过。分辨率、步数、采样器、随机种子按镜头参数覆盖。节点定位基于类名与标题（`POSITIVE` / `NEGATIVE` / 含 `width` 与 `height` 的节点），不依赖节点 id，因而对工作流重排具备鲁棒性。

### 3.3 视频生成通道抽象

视频能力抽象为统一接口 `clip(shot, out) -> Result(provider, task_id, duration)`，四类后端按优先级装配：

| 通道 | 协议 | 适用 |
|---|---|---|
| MiniMax H3（云） | `POST /v2/video_generation` → task_id；`GET /v2/query/video_generation/{id}` 轮询 | 追求质量 |
| 本地兼容网关 | 同上，路径可配置，免密钥 | 本地部署 H3 或自建服务 |
| ComfyUI 工作流 | `/prompt` + `/history` 轮询，下载 `gifs`/`videos` 产物 | 开源视频模型（WAN / Hunyuan 等） |
| 占位实现 | ffmpeg `lavfi` 渐变源 | 无模型时的流程验证 |

本地通道的 HTTP 会话显式关闭环境代理继承（`trust_env=False`）。这一处理并非防御性编程的偏好，而是必要修复：在启用系统代理的机器上，`127.0.0.1` 请求会被代理接管，导致本地服务"明明在运行却连不上"。

### 3.4 配音驱动的时长锁定

多数同类实现先定时长再合成语音，音频不足则补静音、超长则加速，二者都会引入错位或音色失真。本文采用相反顺序：先生成语音并测量其真实时长 `a_i`，再以 `a_i` 约束镜头时长

```
d_i = clamp(a_i + δ, d_min, d_max),  δ ≈ 0.3~0.6 s
```

其中 `δ` 为留白，`d_min, d_max` 由模板与人工设定上下界。合成阶段以 `d_i` 为唯一时间基准，语音不再二次伸缩。语音合成采用三级兜底：MiniMax T2A → edge-tts（免费）→ 静音轨，任一级失败即降级，保证时间轴始终可闭合。

### 3.5 时间轴重算与转场链合成

设镜头序列时长为 `d_1 … d_n`，第 `i` 条与第 `i+1` 条之间转场时长为 `τ_i`（硬切取 `τ_i = 0`），则第 `k` 条镜头的起始偏移与总时长为

```
o_1 = 0
o_k = Σ_{i<k} (d_i − τ_i)
T   = Σ d_i − Σ τ_i
```

拼接分两条路径：全为硬切时使用 `concat` 解复用器快速拼接；存在转场时构建 `xfade` 链，逐段以 `offset = o_k` 融合。变速镜头先按 `d'_i = d_i / s_i` 折算时长，再参与上式；入点裁剪与变速共同决定实际取用的源区间长度：

```
need_i = d'_i × s_i + trim_i
```

实现中记录了一处 ffmpeg 行为缺陷：当 `xfade` 的 `duration` 为 0 时，滤镜链在部分版本下会丢弃后续输入，输出仅保留前几段（实测输出体积从 8.5 MB 降至 0.3 MB）。因此硬切在转场链中统一退化为 `τ = 0.04 s` 的融合，视觉上不可察觉，却可保证图结构正确。

字幕在转场重叠区间内会被截断至下一镜头起点，避免两条字幕同时出现；每条镜头还可叠加独立文字层（标题），与对白字幕分层渲染，位置分顶部、居中、底部三档。

### 3.6 基于内容指纹的缓存复用

中间产物（归一化片段、配音、字幕）以指纹为键缓存，指纹定义为影响该产物全部参数的哈希：

```
F_norm = H(d, trim, τ, s, filter, brightness, contrast, saturation,
           temperature, mirror, reverse)
F_tts  = H(dialogue, voice_id, speed, volume, pitch)
```

仅当指纹变化时才重新计算，因此"改字幕"只触发字幕与封装，"改时长"才触发归一化与拼接。该策略将交互式修改的等待时间从"整片重算"降至"单段重算 + 一次封装"。

### 3.7 硬件自适应的实证配置

首次启动执行一次环境探测，并将结论写入 `config.json`：

| 探测项 | 决策 |
|---|---|
| CPU 核数 / 内存 / 磁盘余量 | 并发数；内存 < 8 GB 时降至 720p |
| GPU 型号与显存 | ComfyUI 出图尺寸（1024×576 ~ 1536×864） |
| 中文字体 | 选取可用 CJK 字体，避免字幕方块 |
| WebView2 运行时 | 缺失则退回浏览器宿主 |
| ComfyUI / 视频网关 | 探活，决定默认通道 |
| 硬件编码器 | **试编码一帧**后判定 |

最后一项是本节的要点。`ffmpeg -encoders` 仅反映编译期能力：在未安装 NVIDIA 驱动的机器上，`h264_nvenc` 依然出现在列表中，实际调用则报 `Cannot load nvcuda.dll`。因此系统对每个候选编码器执行一次 256×144、单帧的真实编码，仅当退出码为 0 才纳入候选集，否则回落 `libx264`。该判定在本机（无独立显卡）得到正确结果。

## 4 系统实现

### 4.1 技术栈与部署形态

| 层次 | 选型 | 说明 |
|---|---|---|
| 运行时 | Python 3.10+ | 单进程，无外部数据库 |
| 服务 | FastAPI + uvicorn | 27 个 REST 接口，`loop=asyncio`、`http=h11`、`ws=none` |
| 宿主 | pywebview / WebView2 | 缺失时自动切换系统浏览器 |
| 合成 | ffmpeg 9.0.2 | 随包分发，含 `libass` / `libx264` / `xfade` |
| 打包 | PyInstaller（onedir） | 可写根与只读资源根分离 |
| 前端 | 原生 JS + Canvas + 内联 SVG | 无构建步骤、无外网依赖 |

打包形态下，`APP_ROOT`（可执行文件同级，可写）与 `BUNDLE_ROOT`（`_MEIPASS`，只读）被显式区分。此项分离是必要的：若沿用源码期的"包目录即工程根"假设，配置与成片会被写入临时解压目录，进程退出即丢失。

### 4.2 交互与可编辑性

界面按生产阶段划分为工作台、剧本、分镜、时间线、成片、设置六个视图，时间线视图承担全部精修操作：

| 维度 | 能力 |
|---|---|
| 结构 | 拖拽排序、入点裁剪、时长 1~15 s、镜头分割（按第 N 秒，入点与变速自动换算） |
| 视觉 | 11 种转场（各自 0.1~1 s）、7 个调色预设、亮度/对比度/饱和度/色温、镜像、倒放 |
| 时间 | 0.25×~4× 变速 |
| 声音 | 逐镜头音量 0~200%、BGM 上传与淡出、整体响度归一到 −16 LUFS |
| 文本 | 对白字幕、独立标题层（三档位置、字号可调） |
| 素材 | 本地视频替换单条、追加导入、单镜重拍 |
| 语言 | 自然语言剪辑指令（LLM 解析，失败时退回正则规则） |

自然语言指令采用双通道设计：配置了 LLM 时由其输出结构化操作序列，未配置时由本地规则解析"第 2 镜""全部""1.5 倍速""黑白""叠化"等关键词。该设计保证该功能在离线环境下仍可用，而非变成必须联网的摆设。

|---|---|---|---|---|---|---|---|
| R1 | 初次链路验证 | 1920×1080 | 8 | 58.60 s | 5.1 MB | 0 | 含配音、字幕、BGM |
| R2 | 剪辑能力验证 | 1920×1080 | 8 | 56.04 s | 8.5 MB | 4 | 含文字层、黑白、镜像、1.25× |
| R3 | 打包形态复现 | 1920×1080 | 8 | 56.04 s | 8.5 MB | 4 | 与 R2 参数一致，结果一致 |
| R4 | 打包应用全链路 | 1920×1080 | 8 | 45.60 s | 4.3 MB | 0 | 从建项到出片 |
| R5 | 解压即用验证 | 1280×720 | 8 | 44.68 s | 1.8 MB | 0 | 自动配置降至 720p |

R2 与 R3 构成一次可复现性检查：源码形态与打包形态在同一参数下产出一致的时长与体积。R5 验证了"解压到含空格路径 → 自动配置 → 出片"的完整路径，成片流为 H.264 High / yuv420p / 30 fps + AAC 立体声。

### 5.3 性能观察

在 1280×720、8 镜头、占位素材条件下，关键帧与镜头生成阶段耗时 50.2 s，合成阶段（8 段归一化 + 拼接 + 声轨 + 字幕 + 封装）耗时约 85 s，产出 44.68 s 成片。合成耗时高于成片时长，主要来自逐段二次编码；若启用硬件编码器，该比值预计显著下降，但本文未在具备相应硬件的机器上验证，故不作断言。

自然语言指令与单镜分割的接口往返均在秒级完成，说明交互瓶颈位于媒体处理而非编排层。

### 5.4 稳定性问题与修复

开发期共定位并修复 7 类缺陷，均具有可复现的触发条件：

| 现象 | 机理 | 修复 |
|---|---|---|
| 成片仅保留前 3 段，体积 0.3 MB | `xfade duration=0` 导致滤镜图丢弃后续输入 | 硬切退化为 40 ms 融合 |
| 每条片段恒为 1 s | `lavfi` 渐变源 `duration=1`，与 `-t` 冲突 | 按镜头时长生成源 |
| 本地 ComfyUI 连接被拒 | HTTP 会话继承系统代理，`127.0.0.1` 被劫持 | `trust_env=False` |
| 并发写 `project.json` 报 `Permission denied` | 多线程同时替换临时文件 | 加锁 + 原子替换 |
| 变速镜头被拉长 | `-t` 置于 `-i` 之后，作用于输出而非输入 | `-t` 前移至输入侧 |
| 打包后配置与成片写入 `%TEMP%` | 以包目录推导可写路径 | 拆分 `APP_ROOT` / `BUNDLE_ROOT` |
| 打包后窗口无法创建 | `clr.pyd`、`Python.Runtime.dll` 未被收集 | 显式加入二进制依赖 |

## 6 讨论

### 6.1 与商用 NLE 的定位差异

本系统不试图替代非线性编辑器。NLE 的核心抽象是"时间轴上的图层树 + 关键帧曲线"，其表达能力远超"一条镜头序列"。本系统的价值在于把"零素材"推进到"有素材、有结构、有初版"，此后的精修交由 NLE 更为经济。因此更具工程价值的方向是**导出工程交换格式**（EDL / XML / FCPXML），使分镜、入点、转场、字幕可平移至剪映或 Premiere，而非在本地重造一个半成品多轨编辑器。

### 6.2 局限性

1. **真实模型未验证**：受限于无可用密钥与本地模型，MiniMax-H3 云端路径、ComfyUI 视频工作流仅完成协议实现与降级验证；本文所有成片均基于占位素材。系统对协议细节（字段名、状态枚举、产物路径）的假设尚未经真实服务校验。
2. **评测非受控**：样本量为 5 次开发期运行，无基线系统对比，无主观质量评分；所报告的"一致"仅指时长与体积层面的可复现，不含画面语义一致性。
3. **时长约束为软约束**：3.1 节所述 18 s → 52 s 的偏差说明，仅靠提示词约束不足以控制节奏。可行改进为生成后按目标时长做二次规划（合并/拆分镜头），或引入显式 token 预算控制。
4. **无质量评估闭环**：系统不评估生成镜头的语义符合度与美学质量，失败判定仅依赖"文件是否产出"。引入 CLIP 相似度或视觉语言模型打分可显著提升自动重试的有效性。
5. **单轨限制**：不支持叠加轨道，因而无法表达"解说 + 画面 + 字幕 + 贴纸"的复合结构。

### 6.3 合规与伦理

系统可生成包含人物形象的视频，使用者须自行确保素材授权、肖像权与平台合规；本地部署在降低内容外流风险的同时，并不豁免上述责任。系统默认仅监听回环地址，并对 `/api/*` 启用随机 token 与 Host 白名单（token 每次启动轮换）；即便如此，仍不应直接暴露于公网。

## 7 结论与后续工作

本文实现了一套面向个人创作者的本地化 AI 视频生产管线，其核心不在于某一生成模型，而在于把"生成"组织为可恢复、可编辑、可降级的工程过程。逐镜头状态机与指纹缓存解决了重跑成本问题；配音驱动的时长锁定解决了音画对位问题；转场链时间轴重算与硬切退化解决了拼接正确性问题；实证式编码器选择解决了跨机器适配问题。

后续工作按优先级排列：（1）导出 EDL / FCPXML 以衔接专业 NLE；（2）引入镜头级质量评分与自动重试策略；（3）支持双轨（主画面 + 叠加层）以容纳字幕卡与贴纸；（4）在具备 GPU 的机器上补充硬件编码与真实模型的对照实验。
